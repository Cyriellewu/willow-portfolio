About

I'm a software engineer who ended up doing a lot of machine learning. The part I like is where the two meet: deciding what a system should predict, building the pipeline that feeds it, and checking that the number it reports is real.

I studied data science at Hong Kong Baptist University. My final-year project there, with a vehicle manufacturer, became a first-author paper at ACML 2025. Now I'm at Columbia finishing a master's in computer science on the machine learning track. I graduate in December 2026.

In summer 2026 I was a software engineering intern at Microsoft, on the OfficePLUS AI assistant. I worked on the React and TypeScript engine that streams model output into the chat, and spent a few weeks in Azure telemetry working out why users were hitting failures. Since June I've also been a data analyst at Columbia Business School, building entity-resolution pipelines in Python and DuckDB on the university's HPC cluster.

Things I keep coming back to

Define the target before picking the model. In the ACML work, the first real contribution was turning "predict failure" into three questions the maintenance records could actually answer.

Evaluate in a way that can't cheat. Vehicle-wise chronological splits, entity-disjoint folds, fold-safe feature engineering. Boring, and the only reason I trust the results.

Keep a clear line between what code guarantees and what a model suggests. Oracle OS puts every symbol in code and lets the model only explain. At Microsoft, part of the refactor was proving which fallback branches were load-bearing before touching them.
